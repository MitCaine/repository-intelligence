# Lightweight workflow corrections

> Scope: extended/historical consumer mechanisms and observations. For current
> lightweight adoption use [the controller workflow](capsule-controller-workflow.md).
> These examples do not add mandatory gates or establish current project integration.

This guide reconciles the mature-project trials with RI's controller guidance.
It is a proposal for consumer adoption where their installed rules differ;
reading RI does not alter an active consumer's authority, recovery allowance,
profile floors or report schema. Use only resources actually selected by the consumer; the lightweight route
does not require five skills or a special runner. Add no scheduler, approval stage, registry or universal test framework.

## Before starting an issue

Qualify the adopted route once for the relevant host/runtime/helper revision.
Reuse the result while its recorded inputs remain unchanged; per-attempt source
and authority checks still apply. Do not repeat a full adoption ceremony on
every issue. Record:

- the compatible RI runtime and inventory/mapping contract, independently of
  installed skill versions and locally adapted instructions;
- the actual protected command, account, ancestor-directory traversal, source
  read/import and trusted-policy write-denial targets;
- the actual qualification-to-review startup callsites and immutable executable
  authority, with mutable bytecode/cache/log/scratch stored separately;
- the accepted review API schema, permitted callbacks, source/Standards/raw-log
  locators, report output route and final import validator;
- retained Git objects recoverable in a fresh checkout after branch cleanup;
- a completion route qualified in the intended controller host.

Use one harmless end-to-end specimen through the **actual consumer helpers**.
A reimplementation, source hash, mock printed stage, local parser acceptance or
successful dispatch is insufficient. Exercise a positive twin and the observed
negative boundaries: omitted required node, unreadable source, writable trusted
policy, extra/tampered startup authority, premature import, missing report input
and rejected report delivery/import. Existing accepted fixtures should be reused.
Do not rerun solved prerequisites solely because RI has a new recommendation.

For a broken installed qualifier, preserve its failure and identify a finite
separately authorized prerequisite whose incumbent checks can genuinely run.
Candidate workflow edits do not silently replace the installed selecting gate.
A prerequisite review is not product recovery authority. If no supported route
exists, stop with the exact unresolved dependency; do not accept failed Q.

For existing chats, reconstruct the next action from the authenticated checkpoint
and effective adopted revisions. Preserve active jobs, candidates, failures and
remaining budgets. Compare skill folders three ways: recorded upstream template,
local adaptations and proposed new template, including supporting resources.
A chat reset or renamed correction never renews authority.

### Immutable startup authority and mutable caches

Qualification may create bytecode/cache output. Keep that output outside the
runtime tree authenticated before reviewer startup. Under isolated Python,
environment variables such as `PYTHONDONTWRITEBYTECODE` can be ignored; select
`-I -B` or an explicit `-I -X pycache_prefix=/permitted/mutable/cache` where the
actual worker supports it. Do not suppress unexpected authority files by adding
an ignore rule. Authenticate initializer/verifier/worker/executable/SDK bytes
before importing or dispatching candidate-adjacent code.

The actual shared-startup fixture must run qualification first, then call the
same authentication/import/startup path as the real worker with harmless
recording dependencies. Require cache creation to leave immutable authority
unchanged. Tampered initializer/verifier, extra authority files and premature
import must fail before model startup. Permission fixtures independently prove
source ancestor traversal/read/import and write denial against named trusted
policy/runtime/step files; a legitimately writable candidate helper is not the
negative target. Fixture/read-only behavior on macOS does not establish the
Linux account and directory mode behavior. Bind reusable capability to those
actual host, account, path, runtime and helper inputs.

## Validate before readiness and dispatch

Use this order within existing planning, without an extra approval round:

```text
issue/base + complete impact inventory
  -> draft capsule and exact command/wrapper/report route
  -> deterministic validation and applicable protected rehearsal
  -> resolve any required scope challenge
  -> capture final P and publish only at the consumer-authorized stage
  -> verify P, scope, invocation and evidence feasibility
  -> implement -> capture C -> qualify C -> fresh independent review
  -> guarded acceptance -> installed obligations -> terminal closeout/cleanup
```

If a consumer must publish before validating a wrapper, record the intermediate
state as preparation, not READY. Failed validation must not yield an authoritative
readiness identity. Validate report schema, ancillary proof and aggregate/public
packet limits before allocating a reviewer or freezing an expensive invocation.
Use actual output, including the large existing file; a source byte count is not
an evidence size estimate. Keep failed preparation and substantive failure counts.

## Claims require observations

For each behavioral claim, name its mandatory test/node or equally concrete
observation, selecting gate identity and proof stage. Distinguish:

| Stage | What it proves |
| --- | --- |
| Incumbent qualification | What the installed gate actually selected and executed on C |
| Proposed-gate fixture | Candidate gate behavior as an inert subject under an incumbent-controlled oracle |
| Installed control | Actual installed account/path/selector behavior after acceptance |

A green job which never collected a mandatory node does not prove its claim.
A skipped node must retain its identity, reason and capability observation.
Use the optional `mandatory_observations` export in the
[evidence checker](skill-templates/capsule-preflight/references/evidence-contract.md)
when the consumer can export authenticated selecting/execution records. The
checker cannot infer those facts from a total or authenticate an arbitrary log.
Final invocation identity is required even when pre-freeze rehearsal is not
supported. Rehearsal is additional evidence, not permission to omit final binding.

## Concise, complete reviewer input

Prepare one manifest with exact P/C and capsule identities, full diff, changed
source, active ACs, all applicable Standards, check observations and raw-log
locators, accepted report schema, output path and importer. Separate orientation
from retained complete evidence. Expose small named/path selections through the
accepted callback; do not repeatedly dump a receipt or inventory to the model.

Before the live review, send a synthetic report through the actual API schema,
permitted read callbacks, supported report-file delivery and final importer.
Ensure every required proof is reachable in that lane. A successful local
write/copy/hash test alone does not qualify a remote reviewer route. Source/log
export requires its existing authority; do not resolve visibility conflicts by
uploading evidence implicitly. Authorize a supported local lane or bounded export.

The reviewer decides behavior and Standards first, then generates mandatory
mechanical structural dispositions once. Deterministic inventory/hash accounting
can support concise review; it cannot waive a consumer's disposition requirement.
Return one complete report and a small completion message with C, locator and
digest. An incomplete report is not approval regardless of time or tool calls.

## One representation, preserved provenance

Prefer one complete retained structural representation with authenticated views.
Use the optional [review bundle](review-evidence.md) only when it helps the actual
consumer. Original raw-byte hashes and canonical JSON hashes have different
meanings; retain that distinction. Preserve the provenance and timing of separate
observations even when their content can be stored once. Compression reduces
storage, not the number of semantic judgments.

Nutrition's accepted cap/publication prerequisites addressed historical limits;
remaining duplicate copies require its own format migration. A smaller RI bundle
alone does not fix an eleven-name consumer inventory or qualification receipt
which embeds the same data again. Do not add universal compression/paging.

## Stage obligations and bounded reuse

Give original obligations stable IDs, explicit resolution routes (external prerequisite
or review-dischargeable), and deadline stages: candidate, installed,
terminal. Candidate approval must not require a later event dependent on that
approval. Stage deferral never excuses a known production defect or failed
applicable criterion. Return later obligations as pending/deferred, never passed. At installed
and terminal stages, require their real observations before completing the task.

After consumer adoption, terminal review can focus on the lifecycle diff,
current source/evidence equivalence, authenticated accepted receipts and remaining
obligations. Reopen earlier judgments when production inputs, requirements or
retained proof change. Retain original outcome accounting even when an unchanged
implementation judgment need not be repeated. If the installed contract requires
fresh original-outcome review, follow it until explicitly changed.

Reuse requires authenticated prior evidence and a complete declared input map:
code, dependencies, selecting gate, configuration, toolchain, relevant environment,
isolation and timeout policy. Unknown inputs disable reuse. The pure
`equivalent_inputs`, `carry_review` and `validate_obligation_stage` predicates in
the [existing helper](skill-templates/capsule-preflight/scripts/evidence_preflight.py)
illustrate these comparisons; they grant no permission and do not maintain state.
Keep the original run/reviewer/C provenance and bind the eligibility decision to
current C. Never relabel inherited proof as a fresh execution on current C.

Select expensive checks by affected claim/component and demonstrated detection
benefit under an adopted consumer policy. The Nutrition ledger reports repeated
literal backend/mobile launchers and only one hosted iOS selection. It does not
justify treating those as repeated hosted iOS or assigning an invented share of
12 hours. Preserve substantive installed trust/PG/native proof wherever affected.
A Linux access-only change should have its native profile floor assessed by its
owner, rather than RI waiving that floor or adding another broad suite.

### Cost-to-protection evaluation

The retained Nutrition audit supports these bounded recommendations. Counts
are historical observations, not fresh consumer qualification or additive wall
time. No runtime saving is inferred from the local eligibility predicates.

| Work | Evidenced protection/cost | Recommendation |
| --- | --- | --- |
| Full literal backend/mobile launcher across packaging corrections | At least twelve launcher attempts; one broader run reported 1,925 backend tests. Incremental protection for unchanged production inputs was not demonstrated. | Permit unchanged-component proof only after complete-input equivalence and consumer adoption. |
| Hosted repository qualification | Selected in fifteen retained App checks; establishes actual incumbent run/source, but can omit newly required nodes. | Retain current identity binding and mandatory-node observations; assess unaffected check reuse separately. |
| Hosted backend/PostgreSQL/native | Selected backend five, PostgreSQL three, iOS once; selection does not prove each substantive suite ran. | Retain affected substantive controls and their collected/executed observations; assess path-only native floors with owner. |
| Installed account/path/gate controls | Four invalid controls exposed a real capability gap that pre-install proof missed. | Retain positive/negative actual installed proof; qualify stable setup before product work. |
| Independent review and terminal re-review | Thirteen sessions, 677 reads, 82 failed reads; a terminal-only packet was rejected under original-outcome rules. | Retain semantic independence; adopt scoped terminal carry-forward where source/requirements/proof are unchanged. |
| Evidence representation/publication | Duplicate views exceeded one limit; a later compact wrapper exceeded another. | Measure all boundaries before freeze; retain one complete logical representation and provenance. |

The local stage/equivalence fixtures demonstrate eligibility decisions and cycle
avoidance, not eliminated model calls in a production trial. Consumer adoption
must measure actual broad checks/reviews removed and any missed-defect risk.

## Corrections and uncertain operations

| Case | Smallest permitted next action |
| --- | --- |
| In-scope preparation error before C | Repair and revalidate the affected preparation; avoid new implementation unless consumer authority requires it. |
| Missing evidence, unchanged C | Retain the failure and use permitted supplementation or the necessary rerun, then applicable independent review. |
| Transport failure before model startup | Reconcile actual dispatch/start state; use only the existing finite retry allowance. |
| Changed source or substantive scope | Rebind C or replan as required; do not carry affected proof. |
| Broken installed execution path | Separate honest prerequisite or stop; no false success or renewed recovery grant. |

Use the existing attempt store with a stable operation identity. Distinguish
permission allocation, dispatch, model startup, completed verdict and imported
receipt. Record preparation before dispatch; if an external action's return is
lost, inspect the actual run/ref/receipt before retry. Exercise faults after
dispatch, completion and integration: an unknown response is not proof nothing
happened. Reconcile the same operation; do not allocate a duplicate launch/import/
merge. This is not a promise of exactly-once external delivery. Retain finite
budgets and their counts across renamed attempts.

## Completion and waiting

Keep command completion, CLI notification acceptance, controller consumption and
next action distinct. Queue delivery recovery never restarts completed work.
On a nudge, reconcile its identity against the active stored attempt and ignore
stale/duplicate notifications without duplicate consequential actions.

Qualify success and failure/timeout through the actual host's end-of-turn boundary
before claiming autonomous continuation. RI cannot establish Work-host wake-up
using a local Codex CLI fixture. Until qualified, use the host's supported bounded
blocking wait on the existing job. If that route is unavailable, record the
manual-resume limitation once. Do not fill the gap with repeated controller polls.

Wait-time optimization remains deferred. If separately selected later, choose one
named preparation output with exact inputs and a stopping point before waiting.
Keep it provisional/external; never publish another READY/P or execute a second
capsule. Changed accepted base or active-task failure invalidates dependent
preparation. With no selected task, or once its output is complete, sleep. There
is no demonstrated turn saving yet; activity is not an effectiveness result.

### Simulation clarification: origin versus eligibility

The supplied hypothetical harness is contract-level testing, not proof of host
integration. Its combined cases sharpen #87/#91: retained evidence remains tied
to the original command, environment and source candidate. A separate authorized
equivalence decision names the new candidate; it must never rewrite that original
receipt. The preflight template now has a focused validator for this separation.

Obligation deadlines alone are insufficient. External prerequisites must pass
before review intake; obligations that review is authorized to satisfy can enter
review and must pass by completion. The template checks these two phases without
adding a workflow stage. Consumer adoption remains separately authorized.

Terminal carry-forward also requires unchanged retained-evidence digest and adopted
policy version. Selecting-gate identity is a separate required input, not inferred
from an unchanged test selector. Existing exporters must supply it explicitly.

against a retained checkout when evaluating its published helper. It reads only
tracked `HEAD` scripts into temporary scratch; it never dispatches a model or

```sh
python scripts/probes/poker_attempt_boundaries.py --consumer /path/to/poker-app
```

and verified reader. A synthetic eligibility response isolates allocation from
qualification. The fixtures reconcile a retained allocation after a lost response,
